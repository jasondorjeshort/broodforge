# Critic review of proposal 0022

Date: 2026-10-14. Reviewer: critic (Fable 5.1). Sources: bubblewrap source and man page (containers/bubblewrap, main), the AppArmor `bwrap-userns-restrict` profile (apparmor repo, extras), Ubuntu noble package records and the apparmor filelist, Debian bookworm package pages and `README.Debian` for bubblewrap, the sudo and sudoers man pages (sudo.ws) and `src/exec_nopty.c`, `proc_pid_environ(5)`, systemd.exec and systemd-run man pages (man7), git documentation (git-clone, gitrepository-layout, gitcredentials, `config/safe.adoc`, `config/uploadpack.adoc`, release notes 2.39.4 and 2.45.1) and git source (`builtin/clone.c`, `setup.c`, `upload-pack.c`), the kernel `fs.txt` sysctl doc, Node `child_process` docs, the Claude Code docs at code.claude.com (sandboxing, permissions, settings, settings-reference, hooks, headless, env-vars, claude-directory, CHANGELOG), Discord developer docs (docs.discord.com), Microsoft Learn (Start-Process 5.1, CreateProcessWithLogonW, Nested Jobs, JOBOBJECT_BASIC_LIMIT_INFORMATION, taskkill, WSL wsl-config and filesystems, Process.Start), and runs on the owner's PC (Node 22.23.2, Windows PowerShell 5.1.26100, Claude Code 2.1.296) for V11, V13 and V15.

## Verdict in one paragraph

The architecture is right: two unix users plus bubblewrap on the droplet, one encrypted store with the key outside the backup set, config-dir delivery, a tree per session that never shares the canonical `.git`, and an honest Windows first version. Four load-bearing facts are wrong or missing, and each one changes a line of the recommendation rather than the shape. V6 is false: Claude Code watches its settings files and reloads `permissions` and `hooks` while running, so a session that can write its own config dir can drop the hook mid-turn. V8 is true but P2 as written does not run: git refuses a local clone of a repository owned by another user and `upload-pack` refuses to serve one, so both the per-session clone and the end-of-session fetch die on "dubious ownership", and the obvious fix (`safe.directory` for the session's clone) hands the session a way to run code as the bot. L2's `--clearenv --setenv` puts the API key on bwrap's command line, in `/proc` for every user and in sudo's log. And the Linux interrupt chain ends in a SIGKILL, not a `result`, because bwrap forwards nothing and `--die-with-parent` is `PR_SET_PDEATHSIG, SIGKILL`. On Windows, the better first-version answer is not W1 or W2 but running the whole instance as a second standard account, which the proposal did not consider. Nothing here revives L3, L4, S2 or P1.

## Objections

1. **Blocking. V6 is false: a session can delete the hook and the deny rules while its turn runs.** The settings doc: Claude Code "watches your settings files and reloads them when they change ... including edits to `permissions`, `hooks`"; the hooks doc says direct edits "are normally picked up automatically by the file watcher". Under L2 the config dir is `--bind` read-write (the engine must write `.credentials.json` and `projects/`), owned by the engine user, and the session's Bash runs as that user, so `echo '{}' > $CLAUDE_CONFIG_DIR/settings.json` removes the PreToolUse hook, every `Read`/`Edit` deny and the sandbox block for the rest of the turn. The binds still hold, so reach survives on Linux; what falls is everything the ADR 0020 hook does: the outside-reach deny text, prompt mode's `defer`, the policy-mode allow, and the sandbox settings. On Windows nothing survives, which W2 already admits. The proposal states "settings are read at process start" as the reason a change cannot carry to the next turn; the next turn is rewritten anyway, the current turn is the hole. Resolve: on Linux `--ro-bind <configdir>/settings.json <configdir>/settings.json` after the directory bind (bwrap binds single files, verified in source), which makes the file unwritable inside the sandbox while the engine keeps writing the rest of the directory; alternatively C26 (an empty `--setting-sources` plus `--settings` with the JSON inline) if the watcher does not cover `--settings`, which the docs do not say. On Windows state the gap. The spike must include "the session rewrites settings.json mid-turn" as a case.

2. **Blocking. P2 does not run across users, and the natural fix is unsafe.** `git clone <canonical>` by the engine user from a bot-owned directory dies: `copy_or_link_directory()` in `clone.c` calls `die_upon_dubious_ownership()` and never falls back; git-clone's text: "does not work with repositories owned by other users for security reasons, and `--no-local` must be specified". `--no-local` and `--shared` go through `upload-pack`, whose `enter_repo()` dies the same way (`setup.c`). The end-of-session `git fetch <session tree> <branch>` run by the bot dies likewise, because `upload-pack` runs in the engine-owned clone. `-c safe.directory=<path>` on the command line lifts each (command scope is protected configuration). For the engine's clone that is fine: the canonical is bot-owned. For the bot's fetch it is not: `safe.directory` means git "parses the config of a repository owned by someone else", and `upload-pack` reads `uploadpack.*` from the served repository's config (only `packObjectsHook` is protected), so the bot runs git with a session-written config in effect. The proposal's "the engine never sees [the git credential]" then rests on git's own protected-config list, which is a moving target. Resolve: keep P2 but change the handoff direction so the bot never opens the session's repository: the end-of-turn step runs inside the sandbox as the engine user, `git bundle create <session>/out.bundle <branch>`, and the bot runs `git -C <canonical> fetch <session>/out.bundle <branch>:refs/sessions/<id>`; a bundle is objects and refs, no config, no hooks. For the clone, `git clone -c safe.directory=<canonical> --shared` with the canonical's `.git/objects` ro-bound at its own path keeps the owner's "same object store" (the alternates file points at a read-only mount; new objects land in the session's clone), and the bot keeps `refs/sessions/<id>` in the canonical so its gc never prunes a session's base. Hardlinks are not available across users (`protected_hardlinks`) and the proposal's "hardlinks where ownership allows" would never fire on the droplet; drop that sentence. Subagent worktrees inside the clone (R-31) are unaffected. State in the ADR that the reinterpretation of "worktree" keeps everything the owner asked for except a shared `refs/`, and that this is the point.

3. **Serious. L2 as written puts the API key on a command line.** `--clearenv` drops the environment, so the credential must come back through `--setenv ANTHROPIC_API_KEY <value>`, which is an argument of `bwrap`: readable in `/proc/<pid>/cmdline` by every user on the host for the length of the turn, and written to sudo's log, which records "the actual command that was executed, including any command line arguments". This contradicts "no secret is on a command line" twice. Resolve: drop `--clearenv`; sudo's `env_reset` with a per-command `env_keep` is already the whitelist (sudo sets `HOME`, `USER`, `LOGNAME`, `SHELL` to the engine user's and keeps only the listed names), and bwrap passes its environment through unless told otherwise; `--setenv` stays for `HOME` and `PATH` only. If `--clearenv` is wanted anyway, pass the arguments through `--args <fd>`, which needs `closefrom_override` in sudoers, which is the worse trade.

4. **Serious. The Linux interrupt is a kill, not a `result`.** ADR 0020's Linux path is SIGINT to the engine for a `result` with usage. The bot is uid `broodforge`, the engine is `broodforge-engine`; `kill(2)` needs a matching real or saved uid, so the bot cannot signal the engine. The proposal routes the signal through sudo. sudo does relay a user-sent SIGINT to its child, which is bwrap; bwrap installs no handler (verified: the only `sigaction` is SIGCHLD reset to default), so the outer bwrap dies on SIGINT, and the engine, which called `prctl(PR_SET_PDEATHSIG, SIGKILL)` for `--die-with-parent`, is killed. Net effect: every Linux interrupt loses the turn's `result` and usage, the Windows outcome 0020 accepted only because Windows has no signals. Resolve: a second sudoers line, `broodforge ALL=(broodforge-engine) NOPASSWD: /usr/bin/kill`, and the adapter sends `sudo -n -u broodforge-engine kill -INT <engine pid>` to the `claude` process it finds under the bwrap it spawned (host pid namespace, `pgrep -u broodforge-engine -P`); or a control FIFO in the session directory that an in-sandbox supervisor turns into a SIGINT. Add to the spike: "SIGINT mid-turn yields a `result` with `modelUsage`". The `--die-with-parent` SIGKILL remains the right fallback.

5. **Serious. V1 and V5 are decided by an operator choice the proposal does not name.** On Ubuntu 24.04 unprivileged bwrap fails until a profile grants `userns`; the `apparmor` package ships none for bwrap and the extras profile is disabled. Two documented profiles exist with opposite consequences: Claude Code's `flags=(unconfined)` profile, under which bwrap's children are unconfined and a nested bwrap (the engine's own sandbox, L5) can mount, at the price of `/usr/bin/bwrap` becoming a user-namespace trampoline for every account on the box; and `bwrap-userns-restrict`, which stacks children into `unpriv_bwrap` with `audit deny capability`, so the nested sandbox cannot mount and L5 is dead. Neither is the sysctl-off route the proposal's reversal clause names. Debian 12 has no such restriction (`README.Debian`: unprivileged userns on since kernel 5.10, bwrap not setuid). Resolve: the operator doc names the profile (the unconfined-userns one, since the engine's sandbox is the next step), the spike runs one turn with L5 enabled under it and reports whether the inner bwrap starts, and `sandbox.failIfUnavailable: true` is in the written settings so a profile change later refuses rather than degrades. Also pin the engine's bwrap path: the profile attaches by path, and an engine that ships its own bwrap elsewhere gets no profile.

6. **Serious. The proposal says the session's own credential cannot be hidden "under any option"; two documented mechanisms do most of it, and L5 as described is advisory.** `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` strips credentials from "the subprocesses Claude Code starts, such as Bash commands, hooks, and stdio MCP servers" (`ANTHROPIC_API_KEY` removed; `CLAUDE_CONFIG_DIR` removed; `GIT_CONFIG_*` kept) and "on Linux, the scrub also runs Bash subprocesses in an isolated PID namespace so they can't read host process environments through `/proc`"; it is host-neutral, so it works on native Windows too. `sandbox.credentials.files` with `deny` blocks sandboxed reads of `.credentials.json` on Linux. Together they hide the key from `env` and `cat` in the session's shell on both hosts (the Windows `/proc` equivalent, reading another process's memory as the same user, remains). Separately, L5 without `allowUnsandboxedCommands: false` lets the model retry a blocked command unsandboxed, and `excludedCommands` is a user-settings key. Resolve: add the scrub variable to every engine environment, `credentials.files` deny for `.credentials.json` and the two sandbox hardening keys to the written settings, rename the hook's environment so no `BROODFORGE_*` name or value looks like a credential to the scrub (it removes "a name that looks like a credential"), and rewrite the N-15 statement: hidden from the session's shell and file tools by engine mechanisms, readable by the engine's own process and therefore by any process of the same uid; a mitigation, not a boundary. The "what would change this" bullet that says it is not achievable is wrong and should go.

7. **Serious. The second Windows account the proposal should have compared is the one that runs the whole instance.** W1 crosses accounts per turn with `CreateProcessWithLogonW`, which needs the target account granted access to the caller's window station and desktop "even for WinSta0\Default", "starts the process in a new window even if CreateNoWindow", and cannot be called from a LocalSystem service: the shape that fails when the bot is a scheduled task with no interactive desktop, which is how the PC instance will run when the owner is not logged in. The proposal budgets a day or two for it. The option it skipped: create one standard account, `broodforge`, install the engine for it, put the instance root and the canonical checkouts in its profile, and run the bot as that account from Task Scheduler ("run whether user is logged on or not" stores the password; `net user /add` is one admin-console command, no interactive prompt). Engine and bot share the account, so sessions read the bot's secrets exactly as W2 admits; but the owner's `~/.claude`, the owner's checkouts and every other project under the owner's profile are unreadable by default profile ACLs, which is the one thing the vision names as never to be touched, and it costs no per-turn plumbing, no job-object race and no file-tailed streams (`taskkill /T` works as the same user). It also removes the W2 line "the owner's own token" from the Windows gap list. Resolve: add it as W0, recommend it for the first version over W2, and keep W1 as the step after it.

8. **Serious. Attribution is set by default, not enforced, and the droplet's commits fail outright.** V15 holds for the author. Two gaps: (a) the committer identity comes from git config, not the author variables; on the PC it is the owner (verified), and inside L2 the engine user has no `user.email` and `--clearenv` leaves no `EMAIL`, so `git commit` dies with "unable to auto-detect email address" on every droplet session until `GIT_COMMITTER_NAME` and `GIT_COMMITTER_EMAIL` are set alongside the author pair; (b) the model can write `git commit --author=... ` or `-c user.name=...`, and R-32's co-author trailers are text the model is asked to write (the engine added none in the probe). Resolve: the spawn sets all four `GIT_*_NAME`/`EMAIL` variables; the ADR states that attribution is a default the environment supplies and a check the bot makes at handoff (on the fetched bundle: author equals the driver, trailers present, otherwise the bot adds them in its own repository with `git interpret-trailers` before the push, or refuses and lists the commits), and hands the check to 03.

9. **Serious. Hidden coupling: the shared network namespace reaches the bot.** L2 does not `--unshare-net`, so a session's shell reaches every listener on the host: another session's dev server, and whatever 05 chooses for the debug transport if it is local HTTP. A troll session that finds the debug port drives the bot. Resolve: 05 must not expose an unauthenticated localhost HTTP surface while sessions run on the same host (a unix socket outside the binds, or a token the session cannot read), and the ADR records the constraint; `--unshare-net` plus a proxy is the egress step the proposal already defers.

10. **Serious. A sudoers mistake fails open to one shared login.** If `CLAUDE_CONFIG_DIR` is not in `env_keep`, sudo drops it silently, the engine falls back to `/home/broodforge-engine/.claude`, and every session on the droplet shares one directory and whatever login lands there first; an API key dropped the same way fails loudly, a config dir does not. Resolve: every sudo call is `sudo -n`; the in-sandbox entry is a Broodforge wrapper that asserts `CLAUDE_CONFIG_DIR` or `ANTHROPIC_API_KEY` is present and exits 1 naming the missing variable; instance start runs `sudo -n -u broodforge-engine env` as a preflight and refuses to start if a kept name is missing, with the sudoers line printed.

11. **Minor. L3's real costs and merits are both understated.** Cost: a polkit rule or an unrestricted `sudo systemd-run` lets the bot start a unit as any user, root included; only a wrapper script as the sudo target bounds it. Merit: `systemctl kill --signal=SIGINT` and `MemoryMax=` solve objection 4 and the resource gap in one layer, and a transient unit is one `journalctl -u` away for an agent. Same-uid sessions still see each other without `PrivatePIDs=` (257; neither distro), which is what keeps L2 ahead. Resolve: say both; the combination (L3 outside for cgroup, kill and limits, L2 inside for binds and `/proc`) is the natural second step and should be named as such, not as a replacement.

12. **Minor. `.claude.json` holds login state and is not excluded.** The settings doc: `~/.claude.json` "holds your sign-in session, MCP server configurations, per-project state"; claude-directory lists it under "App state, OAuth". With `CLAUDE_CONFIG_DIR` it sits in the config dir inside the backup set, and the exclusion names `.credentials.json` only. Resolve: the spike reads what the engine writes there after a login; exclude it by name too, or show it holds no secret.

13. **Minor. Who creates and removes a session directory on Linux is unsaid.** `sessions/` is `0750 broodforge-engine:broodforge-engine`; the bot has no write bit, so creating and deleting `sessions/<id>` are engine-user operations through the same sudo and bwrap route. The worktree-removal interface on Linux is therefore a sudo command, and the 0021 removal procedure and `scratch prune` must call it. Say so.

14. **Minor. `HOME` as the session tree pollutes the tree.** `~/.gitconfig`, `~/.npm`, `~/.cache` land next to the project; harmless to the bundle, noisy for the backup and for `git status`. Resolve: `sessions/<id>/home` and `sessions/<id>/tree`.

15. **Minor. Refusal messages.** The hook's deny says "the channel's configuration sets reach", but ADR 0021 says a running session keeps the reach it started with, so the lift is "change the channel and start a new session"; the message should say so. A write under an `--ro-bind` returns `EROFS: Read-only file system` with no Broodforge text, and the model will try `sudo`, `/tmp` and `chmod`; the system-prompt append should state the reach so the shell error is expected, and the hook should pre-deny the obvious Bash forms with the named message (it already does, heuristically).

16. **Minor. Housekeeping.** bubblewrap's license file is LGPL 2.1, not 2.0; `LoadCredentialEncrypted=` is since 247, and the V12 trigger is already met by the distributions V4 assumes, so fold it into the decision or drop the trigger. `fs.rename` on Windows fails with `EPERM` while another handle holds the target open (verified), so the store's readers must open, read and close, never hold the file. The relay should map Discord error 50007 to "enable direct messages from server members and retry", since the bot cannot tell beforehand. The `GIT_ASKPASS` or `-c credential.helper='!...'` snippet must read the secret from the environment of that one git process, not inline it.

## Refusals, denials and fail-closed paths, and who lifts them

| Mechanism | Who lifts it, from where, while a session runs | Message says so? |
|---|---|---|
| Hook deny outside reach | Nobody for this session; the owner edits the channel's reach in `config/`, `reload`, and starts a new session (ADR 0021: a running session keeps its reach). | Names the reach and the configuration, not that a new session is needed (objection 15). |
| bwrap read-only or absent paths | Same as above; the bind list is built from the reach at spawn. | No: `EROFS` or `ENOENT` from the shell (objection 15). |
| Settings-sources and strict MCP flags | Nobody; code. Not a refusal. | n/a |
| Sandbox `failIfUnavailable` (if adopted) | The operator installs `bubblewrap`, `socat` and the AppArmor profile; the engine then starts. | Engine error at start; the adapter must surface it. |
| sudoers rule missing or `env_keep` incomplete | The operator edits sudoers. With `-n`, a missing rule fails at once; a missing `env_keep` name fails open (objection 10). | `sudo: a password is required` for the rule; silence for the variable. |
| Key file missing | The owner supplies it (0021 restore step 5); refuses start naming the config key. | Yes, per S1. |
| `.credentials.json` excluded from backup | Nobody; users log in again after a restore. | The restore procedure lists it. |
| Relay off | The owner's instance config change, audited. | Documented. |
| `credential remove` | The user; sessions with it refuse to start. | Per R-41. |
| Settings watcher rewriting rules mid-turn | The session itself, which is the objection (1). | n/a |

## The strongest case against the recommendation, and for the alternatives named in the brief

Against L2 and for L3: systemd-run gives the three things L2 lacks (a graceful signal path, a cgroup per turn, memory and CPU caps) as unit properties the agents can inspect with `systemctl` and `journalctl`, and it needs no AppArmor profile. It loses on the one thing the droplet's threat model cares about most: same-uid sessions see each other's `/proc` until systemd 257, and the polkit grant is root-equivalent unless wrapped. The proposal's ordering stands; the right reading is L2 now, L3 outside it next.

Against P2 and for worktrees under the instance root with the engine user owning the canonical: it keeps git's cheapest model and the owner's words literally. But then every session shares one `refs/heads/` and one `.git/hooks` and `.git/config` with every other session and with whichever process pushes, so a code-reach session can move `main`, plant a `pre-push` hook or a `core.hooksPath`, and the push that follows runs it under the git credential. Read-only reach can no longer bind the checkout read-only, because the worktree metadata must be written. On the droplet that is a worse hole than the clone's cost. On Windows under one account the distinction is moot, and P2 is kept there for parity, which 06 requires. P2 wins once objection 2 is fixed; it also wins the "cheap" point back with `--shared` and ro-bound objects.

Against W2 and for a second Windows account in the first version: yes, but as W0 (the whole instance under the account), not W1 (per-turn cross-account spawn). Objection 7 makes the case.

## Recommendation

Accept the shape with the changes above: L1 plus L2 with the settings file ro-bound, no `--clearenv`, a `kill` sudoers line and `sudo -n` everywhere, the scrub variable and the sandbox hardening keys in every engine environment, the AppArmor profile named as an operator step and tested with L5 nested; S1 as proposed; D1 and D2 with all four git identity variables; P2 with a `--shared` clone from the bot-owned canonical and a bundle, never a fetch from the session's repository, as the handoff; on Windows W0 first, W1 later. Spike before the ADR: one droplet turn in each reach printing `ls`, `env`, `cat` of the instance root, another session's directory and the canonical; a mid-turn rewrite of `settings.json`; a SIGINT that yields a `result`; a nested-sandbox start under the chosen profile; a commit inside the sandbox with the committer variables; `.claude.json` after a login. On the WSL2 question: no. The PC instance serves the owner and a few trusted people, the requirements allow a weaker Windows reach, W0 gives the owner's own account the protection the vision asked for, and WSL2 would add a VM lifecycle (a 60-second idle shutdown unless kept alive, an unverified start path from a scheduled task, slow `/mnt/c` or checkouts the owner's Windows tools cannot see) to a host whose only job is to let the owner develop Broodforge while the droplet does the real work; revisit if the owner ever wants the droplet's reach on the PC. Confidence: high on the verified facts (every objection above quotes a primary source or a run on this machine); high that P2-by-bundle and the ro-bound settings file are the right fixes; moderate on W0, which the owner should weigh since a second account changes how they run the bot during development; moderate on the nested-sandbox outcome, which only the spike settles.
