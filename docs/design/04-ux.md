# UX: what people see in Discord

Date: 2026-10-14. Status: owner decisions applied 2026-10-14. Flows and wording are the owner's
(`CLAUDE.md`, Major decisions); each numbered `Owner n:` marker is answered in the list at the end,
alternatives kept as the record. Everything else follows `01-requirements.md`,
`02-domain.md`, `03-architecture.md` and ADRs 0020 and 0022, which this doc does not reopen.
Ticket Tool is the reference: a panel message with a button opens a private channel for the
requester and staff, and closing it leaves a transcript. A session is a ticket.

Conventions. Message text is in fenced blocks exactly as posted; `<...>` is a value filled in.
Each screen has a one-line sketch: `[#channel] text [Button]`. "Ephemeral" is Discord's
reply-only-you-can-see; every refusal is ephemeral (no public shaming, no email in a channel) and
an `action refused` audit event (N-17). Commands are slash commands with named options; the
vision's `.register Jason Dorje Short <jdorje@gmail.com>` would post the email publicly and cannot
reply ephemerally (Owner 1: slash commands).

## Registration

`[#any channel] /register name:Jason Dorje Short email:jdorje@gmail.com` -> ephemeral reply

```
Registered. Commits you drive are authored as Jason Dorje Short <jdorje@gmail.com>.
Next: add a credential with /credential add, then start a session from a project channel.
```

Running it again replaces the pair (R-02): `Updated: was <old name> <old email>, now <new>.`
Refused when the email has no `@` or has spaces, the name is empty or over 100 characters, or
the caller is not a member of the one server the instance serves (R-11). No role is needed to
register; roles decide what the identity may do (R-04). Anyone unregistered who writes in a
venue, clicks a button or starts a session gets (R-03):

```
You are not registered. Run /register with your name and email first; it takes ten seconds.
```

## Credentials

`/credential add kind:subscription|api-key label:<text>`, `list`, `remove id:<id>`, `default
id:<id>` (R-39, R-41), all ephemeral. An id is `cred-` plus four characters; the list shows id,
kind, label, status (`usable`, `needs login`, `removed`) and the date last used.

Subscription on the PC, or on the droplet with the relay off (the default, ADR 0022):

```
Your Claude login directory is ready (cred-7k2m); Broodforge never reads it. The owner finishes
the login on the host (`broodforge credential login cred-7k2m` prints the command), sends you the
sign-in link, and you send back the code Anthropic shows. Once the owner marks it done, /credential list says usable.
```

On the droplet with `relay.loginByDirectMessage` on, `/credential login id:cred-7k2m` gives
`[DM from Broodforge] Sign in at <url>, then paste the code here. The link is valid for 10 min.`
and, on success, `Signed in. cred-7k2m is usable. Broodforge did not see or keep your token;
Claude Code wrote it into your own login directory on the host.` Failures: Discord 50007 -> `I
cannot message you. Enable direct messages from server members in this server's privacy settings
and run /credential login again.`; no code within 10 minutes -> `No code arrived; the login was
cancelled. Run /credential login to try again.`; a non-zero exit -> `Login failed: <last line of
the engine's output>.` The code is never echoed, logged or stored.

API key: `/credential add kind:api-key` opens a Discord modal (a form only the bot receives) with
one field, `Anthropic API key`; the reply is `Stored cred-9q1x (API key, ends in ...a7f2).` A key
pasted anywhere else is refused with `Never paste a key in chat. Use /credential add
kind:api-key, which opens a private form.` and the message is deleted where the bot can.

## The project channel and the panel

Each project channel holds one pinned panel message the bot posts, Ticket Tool's "Create ticket"
panel; the owner posts or refreshes it with `broodforge panel post <channel id>` on the host.

`[#broodforge] Work on Broodforge with Claude Code: one session is one branch; ending it makes a pull request. May start: Trusted. [Start session]`

A click runs the start flow; `/session start` in the project channel does the same for typists.
A plain message there from a permitted user gets an ephemeral `Start a session with the button
above or /session start; this channel is the lobby.`, so a stray message never clones a
repository or spends tokens (Owner 2: a session starts only by the command or the button).

Refusals at start (ephemeral): unregistered (above); no role in the channel's `start` list -> `Your
roles do not allow starting a session in #broodforge. Ask a server admin.`; the `session-refused` flow
of 03 -> `Could not start a session: <reason>.` with reasons `your default credential cred-7k2m needs
a login` (the store's status, 03), `cred-7k2m was removed; set another with /credential default` or
`cloning the repository failed on the host: <one line>`. A refusal creates nothing.

## Venue: where a session lives

Owner 3 (vision Q 3): version 1 uses A, a private channel per session; B, a thread, is a later
channel option (the library does both, ADR 0020).

A, private channel, Ticket Tool's shape. The bot creates `#s0001-jason` under the project's
`venue.category` (03), visible to the driver, the bot and every role in the channel's `contribute`
and `answer` lists; nobody else sees it. Notifications work like any channel; the count stays
bounded by closing sessions (Discord caps a server at 500 channels); the bot needs Manage
Channels. Closing deletes the channel after the transcript is posted.

`[Sessions] #s0001-jason  #s0002-sam       [#broodforge] panel, summaries, transcripts`

B, later: a private thread `s0001 · <first words of the first message>` in the project channel.
No channel limit, no extra permission; but it auto-archives (the bot unarchives on each message),
shows in the sidebar only while followed, and the owner has said threads hide badly.

Both carry the same messages; the project channel itself is out (R-16 wants several sessions per
channel). The rest of this doc draws A.

## Starting and the first message

The venue exists within seconds of the click (clone and tree, ADR 0022) and opens with a pinned
header: `[#s0001-jason] project, branch, mode, credential, who may answer  [End session]`

```
Session s0001 on Broodforge, branch broodforge/pc/s0001, driver Jason.
Mode: asks first (this channel's default). Credential: cred-7k2m (Claude subscription).
Reach: code. Ends after 60 minutes without activity. Who may answer prompts: the driver.
Write what you want done. Everyone who writes here is handed to the agent by name.
```

Until the first message nothing runs and no tokens are spent. A contributor's first message adds
them (R-13): `Sam joined as a contributor.`; `/session invite user:@Sam` by the driver grants the
venue to a user with a `contribute` role, else `Sam's roles do not allow contributing in
#broodforge.` (ephemeral).

## The turn loop

A participant's message starts a turn (03, Data flow). The bot posts one working message and
edits it in place at most once per second (R-21); it is the live view:
`[#s0001-jason] Working · turn 3 · 0:12  <streamed text>  [Read] ...  [Edit] ...  [Stop]`

```
Working · turn 3 · 0:12
Let me look at how the config loader reads the file.
[Read] src/config/load.ts
[Grep] schemaVersion in src/
[Edit] src/config/load.ts (+4 -1)
[Bash] npm test -> exit 1 (3.2 s)
```

Trace lines: one per tool call, `[<tool>] <target>`: a path relative to the tree for file tools,
the first 80 characters of a command, the pattern for a search; a result is appended only when it
is an error. Subagent calls are indented under their `Task` line. Every posted text, trace lines
included, passes 03's outbound mask (a credential-shaped token shows as `[masked]`). Near
Discord's limit the message is frozen and a new one continues it (R-22); only the newest is edited. A
message written during a turn is queued (ADR 0020), marked with an hourglass reaction, and all
queued messages become one turn with one `From:` block each (03).

Turn end, delete-and-replace: the working message is deleted and its final content posted again
as a new message, so Discord notifies (R-23) and the venue holds one message per turn, in order,
nothing lost. The footer is its last line:

```
Done · turn 3 · 1:42 · 48.2k in / 1.1k out · session 212k · Opus · asks first
```

Owner 4: the trace lines stay in the final message (the owner debugs through this). Owner 5: the
footer carries token figures in every turn.

## Permission prompts (prompt mode)

The hook defers a call inside reach (ADR 0020); the engine exits and the bot posts a new message
mentioning the driver so a phone buzzes: `[#s0001-jason] @Jason Permission · [Bash] npm install left-pad  [Allow] [Deny] [Allow Bash this session]`

```
@Jason Permission needed · turn 3
[Bash] npm install left-pad
Command: npm install left-pad --save
```

The full command is shown, after 03's outbound mask. Buttons, custom id `bf:<session>:<tool_use_id>:<allow|deny|allow-session>` (03; Start, Stop and
End are `bf:<channel>:start`, `bf:<session>:stop`, `bf:<session>:end`): `Allow` once, `Deny`,
and `Allow <tool> this session`, which adds the tool to `BROODFORGE_SESSION_ALLOW` for the rest
of the session (the hook contract makes that variable conditional on this button). Owner 6: the
third button exists, per tool name; without it a code session in prompt mode is a click per
command and people switch to policy mode wholesale, which grants more. Who may
press: the channel's `answer` list, default the driver (R-25); anyone else gets `Only Jason (the
driver) can answer this.` After a click the buttons are removed, the message becomes `Allowed by
Jason` or `Denied by Jason`, and the turn resumes in a new working message; the agent sees a deny
and usually tries another way or stops and says so. Parallel calls in prompt mode (ADR 0020, C28,
observed for a deferred pair): the engine keeps the message's last call and drops the rest, which
the agent asks for again after the answer, one prompt each; the prompt message carries: `The
agent asked for 3 actions at once; this is the last. The others will be asked again one at a time.`
Nobody answering (Owner 16): after the channel's prompt timeout (default 5 minutes) the call is
denied, the message becomes `No answer; denied`, and the turn finishes with its output kept: `[Bash]
npm install left-pad -> denied: the prompt timed out after 5 minutes.` The session stays open; this timer and the idle timeout (R-15) are independent, and the latter still ends it.

Denied by reach, both modes, as a trace line (ADR 0020's deny text, shortened; the agent sees it
in full): `[Edit] ../utopia/config.ini -> denied: outside this channel's reach (code). Nobody in
this session can allow it.` Hook failure (03's tool-denied notice): `[Bash] npm test -> blocked:
the permission check failed on the host; the agent continues without it.` Hook bypassed (03's
hook-bypassed flow, C39), outcome then cause: `[Bash] echo ok -> ran without Broodforge's check:
the permission check timed out on the host.`; the other outcome is `refused by the engine without
Broodforge's check`, the other cause `the permission check failed on the host` (a hook exit the engine ignored).

## Policy mode

The channel's default or the driver's switch. Prompts are answered on the host inside reach; the
trace shows every call, so policy mode reads like prompt mode without the waits. Switch: `/session
mode asks-first|acts-freely`, driver only, effective at the next turn (ADR 0020); the header and footer show the current mode.

```
From the next turn: acts freely. Broodforge answers permission prompts itself, inside this
channel's reach (code). Switch back with /session mode asks-first.
```

Owner 7: the names people see are `asks first` / `acts freely (within reach)`.

## Stop

`[Stop]` on the working message or `/session stop`, by anyone in the `answer` list; the turn is
interrupted (ADR 0020) and the working message is replaced by:

```
Stopped by Jason after 0:48. What was done so far stays in the tree. Say what to do next.
Stopped · turn 3 · 0:48 · 31.0k in / out unknown · session 195k · Opus · asks first
```

On Windows the output count is always unknown after a stop (a kill); on Linux it is known when
the engine answers the interrupt, and 03's turn-interrupted timeout gives `Stop took too long; the
agent's process was killed. Output tokens for this turn are unknown.` Owner 8: Stop and End are open to the `answer` list (stopping is less than allowing).

## Model and effort (vision Q 5)

A switch is a per-process flag; context survives it (`--resume`, ADR 0020). Owner 9 (channel
configuration only) was reversed 2026-10-22, after the first live run (R-29): the driver picks at
start, `/session start model:opus|sonnet|haiku|fable` (else the channel's `model`), and switches in
the venue from the next turn, like mode. `/model` alone replies `Model: Opus (this channel's default).
Switch with /model opus, sonnet, haiku or fable.`; `/model sonnet` (or `/session model sonnet`) and
`/session effort low|medium|high|max` post `From the next turn: Sonnet.` or `From the next turn:
effort high.`; else `Not a model: <value>. Models: opus, sonnet, haiku, fable.` The header gains
`Model: Opus (this channel's default). Effort: high.`, edited on a switch. Rules: `05-debug-interface-discord.md`.

## Idle timeout

The channel's `idleTimeoutMinutes`, else the instance default; 0 or absent is never, the default
since 2026-10-23 (the owner: sessions should not end on their own). The header then reads
`Never ends for inactivity.` in place of `Ends after 60 minutes without activity.` The driver
changes a running session's: `/session timeout never|<minutes>|<duration>` (`30`, `90m`, `2h`; at
least a minute), effective now, the clock restarting if the session is waiting. It posts `Ends
after 120 minutes without activity.` or `Never ends for inactivity.` and edits the header; else `Not
a timeout: <value>. Give never, a number of minutes, or a duration such as 90m or 2h.`

## Ending a session

`[End session]` on the header, `/session end`, the idle timeout if it has one (R-15), or the owner on the
host. A running turn is stopped first; the sequence is 03's (bundle, check, push or pull request)
and the venue shows `Ending: checking and handing off 3 commits...` meanwhile. Owner 10 (vision
Q 2): the default is `pull-request`, so a reviewer sees it before it lands; `push` is a
per-project setting (`handoff`, 03), expected for some projects.

The summary goes to the venue and to the project channel with the transcript attached, so the
lobby shows what happened: `[#broodforge] Session s0001 ended · 3 commits · PR #42 · transcript s0001.md`; a project with `venue.summaryChannel` (03) also gets both there.

```
Session s0001 ended by Jason · 1h 12m · 5 turns · 212k in / 9.4k out · Opus
Branch broodforge/pc/s0001 -> pull request #42 <url>
Commits: a1b2c3d Add config reload · 9f8e7d6 Test last-good fallback · 5c4b3a2 Docs
Author: Jason Dorje Short. Co-authors: Sam Example, Claude Opus 5.5.
Unmerged subagent branches removed: none.
```

No commits: `Session s0001 ended by Jason · 0 commits · nothing to push; the tree was removed.`
The transcript is a Markdown file: every message with writer and time, every trace line, every
permission decision and its decider, every footer. Owner 11: it is attached to the summary in the
project channel (Ticket Tool's habit) and, when set, to the summary channel. A private channel is
deleted ten minutes after the summary. Owner 12: the pull request title and body are written by
the agent in one closing turn asked to summarize its changes (readable; costs a small turn); the
summary shows the title. When the closing turn did not run (a `push` project, an auth error, or
a credential that needs login) the title is `Session <id>: <first message, truncated>` and the
body is the summary.

## Failure flows named in `03-architecture.md`

| Flow | Where | Text |
|---|---|---|
| operator | nowhere for users; the bot is offline | notice channel on the next start: `Broodforge <instance> started: engine <version>, <n> projects. Interrupted sessions: s0003 (#broodforge).` |
| turn-failed | the venue, replaces the working message | `The agent's process ended without a result (exit <code>). Nothing in the tree was lost; tokens so far are recorded. Send your message again, or end the session.` |
| credential-needs-login | the venue, then the ending sequence | `Your Claude login was rejected or has expired. This session is ending and your commits are handed off as usual. Log in again (/credential login, or ask the owner), then start a new session.` |
| tool-denied notice | a trace line | the hook-failure line above |
| hook-bypassed | a trace line | the hook-bypassed lines above, by outcome and cause |
| turn-interrupted | the venue | the Stop timeout line above |
| session-refused | ephemeral at start | `Could not start a session: <reason>.` above |
| handoff-refused | the venue; the session stays open | `Not handed off: 2 commits lack the required attribution. a1b2c3d: missing Co-Authored-By: Sam Example; 9f8e7d6: author is not the driver. Ask the agent to amend them, then end the session again.` |
| handoff-failed | the venue and the project channel | `Push rejected by the remote: <one line>. Your 3 commits are kept on the host as s0001; the owner can retry with broodforge worktree handoff s0001.` |
| notice channel | the owner's notice channel | `Config reload failed: projects/utopia.json: unknown key "reaches". Running on the last good configuration from 2026-10-13 22:10.` and `Nightly backup failed (exit 1). Last good snapshot: 2026-10-13 03:00, 31 h old.` |
| session-ended | the venue, then the summary | `Session s0001 ended: no activity for 60 minutes.` |
| interrupted (R-17) | the venue after a restart | `Broodforge restarted; this session was interrupted. Its tree is kept with 2 commits. Resuming the conversation is not supported yet; /session end hands off what exists, or start a new session.` |
| none (gateway, N-25) | nothing | a rate-limited or reconnecting gateway shows nothing; output catches up |

## Usage, and what is later

`/usage` (ephemeral): `You: 1.2M in / 45k out across 7 sessions; as payer: 1.4M / 52k.`; the
owner adds `all` for everyone (R-45). Money needs a price table and is later (02, Usage record).
Later, marked: the "simple questions" thread (R-19), a read-only channel running a small model with
a tight limit, one thread per question; per-user GitHub credentials; caps; resume after a restart; Ticket Tool integration (vision, Explicitly later).

## Owner decisions (answered 2026-10-14)

1. Decided 2026-10-14: slash commands, ephemeral replies. Not: dot-prefix text commands.
2. Decided 2026-10-14: a plain message gets a hint; a session starts only by command or button. Not: the message as the first turn.
3. Decided 2026-10-14: private channel per session now; thread later as a channel option.
4. Decided 2026-10-14: full trace lines. Not: collapsed counts behind a channel setting.
5. Decided 2026-10-14: token figures in every footer. Not: only in `/usage` and the summary.
6. Decided 2026-10-14: the `Allow <tool> this session` button exists. Not: allow-once and deny only.
7. Decided 2026-10-14: `asks first` / `acts freely`. Not: other words.
8. Decided 2026-10-14: Stop and End by the channel's `answer` list. Not: the driver only.
9. Decided 2026-10-14: model and effort by channel configuration only (vision Q 5). Reversed 2026-10-22 (Model and effort).
10. Decided 2026-10-14: pull request default; `push` per project (vision Q 2, 03 End of session).
11. Decided 2026-10-14: transcript attached to the summary in the project channel, plus an optional per-project summary channel. Not: a DM.
12. Decided 2026-10-14: one closing agent turn writes the pull request text. Not: host-built.
13. Decided 2026-10-14: one driver, no handover in v1 (vision Q 4, 03 Registration and participants).
14. Decided 2026-10-14: the co-author form `Claude Opus 5.5 <noreply@anthropic.com>` stands, and every human and every model that contributed is credited, subagent models included (03).
15. Decided 2026-10-14: the droplet's DM login relay is off at launch (vision Q 1 is ADR 0020).
16. Decided 2026-10-16: an unanswered prompt is denied after a per-channel timeout (default 5 minutes),
    the turn finishes, the session stays open (L4 of `docs/findings/2026-10-16-prior-art-chat-front-ends-for-coding-agents.md`).
